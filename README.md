# ALT — AI-Powered Digital Student Twin (Prototype)

CSI1006 Mini Project. This is a genuine, working minimal slice of the system
described in the Review-2 deck — real trained ML models behind a real API,
driving a real dashboard. Nothing here is a mocked screenshot.

## What's in this folder

| File | What it is |
|---|---|
| `generate_data.py` | Creates `student_data.csv` — 600 synthetic students, 6 behavioural/academic features, plus a GPA and academic-risk label generated with realistic random noise (not hand-picked). |
| `student_data.csv` | The generated dataset. Now only the **seed**: on first start `db.py` loads it into the database, which is the source of truth from then on. |
| `db.py` | The database layer (SQLAlchemy): `students` and `users` tables, auto-created and seeded on first run. PostgreSQL when `DATABASE_URL` is set, otherwise a local SQLite file (`alt.db`). |
| `render.yaml` | One-click Render Blueprint: a web service plus a managed Postgres database. See "Deploying" below. |
| `.env.example` | Template for the optional environment variables. Copy to `.env`; never commit `.env`. |
| `train_models.py` | Trains two scikit-learn RandomForest models on the dataset and saves them to `models/`. |
| `models/` | Trained model files (`gpa_model.pkl`, `risk_model.pkl`), the feature list, the risk decision threshold, and `metrics.json` with honest held-out test performance. |
| `app.py` | FastAPI backend **and** dashboard host. Loads the trained models, serves predictions + recommendations (Gemini-first, rule-based fallback), enforces login on every `/api/...` route, and also serves `dashboard.html` itself at `/`. |
| `auth.py` | The login system: bcrypt password verification, signed JWT session tokens, and the server-side authorization checks (`require_admin`, `require_own_student_or_admin`) used on every protected route. |
| `create_users.py` | Re-runnable script that (re)builds `users.json` — the demo account store — from the plaintext demo passwords, bcrypt-hashing them. Run it again to change a demo password. |
| `users.json` | Generated by `create_users.py`. Bcrypt hashes only. Seeds the `users` table on first start. |
| `gemini_chat.py` | The Gemini API integration — generates recommendations and powers the free-form chat endpoint. Every call is wrapped so a failure never breaks the app (see "The AI chatbot" below). |
| `dashboard.html` | The frontend — a single HTML/JS file: a login screen plus a 5-page app (Overview, Student Twin, Cohort Analytics, Assistant, About & Model) with a persistent sidebar and client-side routing. An admin sees all 5 pages; a student account sees only My Twin, Assistant, and About. Uses the bundled `chart.umd.js`, no internet connection needed for the page itself. Fetches the API on the same origin it was loaded from, with the session token attached to every request. |
| `chart.umd.js` | Chart.js, vendored locally so the dashboard works fully offline. |
| `requirements.txt` | Python dependencies for the backend. |
| `.env` | **Not committed/shipped** — you create this yourself with your `GEMINI_API_KEY`. See below. |

## How to run it

**Only one thing needs to run.** Do NOT open `dashboard.html` directly by
double-clicking it, and do NOT serve it with VS Code's Live Server or any
other separate dev server — that puts it on a different port than the API
and it won't be able to reach it. The FastAPI app serves the dashboard
itself, on the same port as the API, so there's exactly one command and one
URL:

1. Install dependencies (Python 3.9+):
   ```bash
   pip install -r requirements.txt
   ```
2. (Optional — the trained models are already included) Regenerate data and retrain:
   ```bash
   python generate_data.py
   python train_models.py
   ```
3. Start the app:
   ```bash
   uvicorn app:app --reload --port 8000
   ```
4. Open **http://localhost:8000** in a browser. Keep the terminal running the command above open — closing it stops the server and the page will show a connection error.

If you ever see "Could not load data" on the page, it almost always means
that terminal was closed or the command above isn't running — restart it
and reload the page.

## Logging in

The dashboard now opens on a login screen — the API rejects any request
without a valid session token, checked server-side on every route (see
"Login & role-based access" below). Demo accounts (also shown with
one-click "use" buttons right on the login screen):

| Username | Password | Role | Sees |
|---|---|---|---|
| `admin` | `admin123` | Admin (faculty) | Every page: Overview, Student Twin (any of the 600 students), Cohort Analytics, Assistant, About |
| `s1000` | `student123` | Student (S1000, GPA ~8.1) | Only their own twin: My Twin, Assistant, About |
| `s1182` | `student123` | Student (S1182, GPA ~6.8, mid-range) | Same as above |
| `s1093` | `student123` | Student (S1093, GPA ~2.9, flagged at-risk) | Same as above |

To add, remove, or reset a demo account, edit the `USERS` list at the top
of `create_users.py` and re-run `python create_users.py` — it regenerates
`users.json` with freshly bcrypt-hashed passwords. Since the database is seeded
only when empty, delete `alt.db` (or reset your Postgres tables) and restart to
pick up changes.

## Login & role-based access

This is a **real** login system, not a UI-only gate: passwords are
bcrypt-hashed (never stored in plaintext), a successful login gets a
signed JWT session token (12-hour expiry), and **every** `/api/...` route
checks that token server-side before doing anything. A student's token is
tied to exactly one `student_id`; the backend rejects (`403`) any attempt
— from the UI, curl, or anything else — to read another student's
predictions, recommendation, or chat, or to reach admin-only routes like
`/api/students` (the full list) or `/api/cohort_summary`. That boundary
lives in `auth.py`'s `require_own_student_or_admin`, not in the frontend,
so it can't be bypassed by editing the page.

It's appropriately scoped for a course prototype, not production-hardened:
the signing secret defaults to a fixed demo value unless you set
`AUTH_SECRET_KEY` (always set it in production — the Render Blueprint
generates one for you). That's an honest trade-off given the timeline
— documented here rather than hidden.

## The 5 pages (admin view; a student account sees My Twin, Assistant, and About only)

- **Overview** — cohort-wide stats (avg GPA, avg attendance, % at-risk), a
  GPA distribution histogram, and an at-risk watchlist (click a row to jump
  straight to that student's Twin page).
- **Student Twin / My Twin** — live GPA/risk prediction, key stats, an AI
  (or rule-based) recommendation, a per-student chat, and four panels aimed
  at a student using their own twin (see "Student-facing features" below).
- **Cohort Analytics** — a scatter plot (attendance vs. predicted GPA,
  colour-coded by risk — click a point to jump to that student), a feature-
  importance chart pulled straight from the trained models, and a
  searchable table of all 600 students.
- **Assistant** — the same chat engine as the Student Twin page, in a
  dedicated full-width view with quick-start suggestion chips, for a
  chatbot-first demo.
- **About & Model** — what's real vs. placeholder, the honest held-out
  model metrics, and the live Gemini/rule-based status.

## Student-facing features (on My Twin)

A student account sees four panels beyond the base prediction/recommendation,
all driven by real API calls rather than static content:

- **Signal health** — a progress bar per input signal (attendance, marks,
  study hours, assignment completion, mood, sleep), colour-coded against the
  same thresholds the rule-based recommendation engine uses, so a student can
  see at a glance which signals are pulling their prediction down.
- **How you compare** — the student's own signals plotted against the cohort
  average for each one, with an up/down arrow and the gap. Pulls from
  `GET /api/cohort_aggregate`, a deliberately student-safe endpoint: it
  returns only class-wide averages, never any other student's individual
  data (see "Login & role-based access" above for why that boundary matters).
- **Daily check-in** — a student logs today's mood (1–5) and sleep hours;
  this is a real write (`POST /api/students/{id}/checkin`) that updates their
  row in the database and immediately re-runs the GPA/risk prediction
  from the updated data — the recommendation, signal bars, and comparison
  panel all refresh live. This is what makes it a genuine *digital twin*
  rather than a static lookup: the prediction changes because the student's
  real data changed. It persists across a server restart because it's
  written straight to the database, not just held in memory.
- **What-if simulator** — sliders for all six signals, debounced and sent to
  `POST /api/predict` (an ad-hoc prediction endpoint, open to any logged-in
  user since it's hypothetical and never touches a real record) to show how
  the model's prediction would change. Shows both the predicted-GPA delta
  and the risk-*probability* delta versus the student's current twin — the
  two don't always move together. For example, for the at-risk demo account
  `s1093` (very low average marks), raising attendance alone barely moves
  the predicted GPA (marks dominate the model's output there) but does pull
  the risk probability down substantially — a real, interesting model
  behaviour that would otherwise look like the slider "not doing anything"
  if only the GPA number were shown.

## Resilience notes (why it stays fast even when Gemini is failing)

If a `GEMINI_API_KEY` is set but invalid, unreachable, or region-blocked,
`gemini_chat.py` includes a small **circuit breaker**: after 2 consecutive
failures it stops attempting the network entirely for 60 seconds and fails
straight to the rule-based fallback, so switching between students in the
UI stays fast instead of eating a multi-model retry on every single
request. It resets automatically the moment a call succeeds.

## The AI chatbot (Gemini)

Recommendations and free-form chat are powered by the **Google Gemini API**
when it's configured, with an automatic, silent fallback to the original
rule-based engine when it isn't (no key set, no internet, quota hit,
model renamed, etc.) — the dashboard is designed to never break because of
this, which matters most exactly when you're demoing it live.

**To turn it on:**
1. Get a free key at [aistudio.google.com/apikey](https://aistudio.google.com/apikey) (Google sign-in, one click to create).
2. Create a file named `.env` in this folder (next to `app.py`) containing:
   ```
   GEMINI_API_KEY=your-key-here
   ```
3. Restart the server. The dashboard's Recommendation panel will show a
   "Gemini-generated" pill instead of "Rule-based", and the chat box
   underneath it will accept questions.

Without a `.env`/key, everything else keeps working exactly as before —
GPA/risk predictions and rule-based tips don't need Gemini at all.

## API endpoints

All routes below except `POST /api/auth/login` and `GET /api/status`
require `Authorization: Bearer <token>` from a successful login.

- `POST /api/auth/login` — `{username, password}` → `{access_token, role, student_id, display_name}`
- `GET /api/auth/me` — the current token's identity
- `GET /api/students` — all 600 synthetic students and their raw features (**admin only**)
- `GET /api/students/{id}` — one student's raw record (admin, or that student)
- `GET /api/predict/{id}` — model-predicted GPA + academic-risk flag for that student (admin, or that student)
- `POST /api/predict` — same prediction for an ad-hoc, hypothetical feature vector not tied to any real `student_id` — powers the what-if simulator (**any logged-in user**, since it never reads or writes a real record)
- `GET /api/recommend/{id}` — prediction + recommendation (Gemini-generated when configured, rule-based tips otherwise); response includes `"source": "gemini" | "rule_based"` (admin, or that student)
- `POST /api/chat` — `{student_id, message, history}` → free-form Q&A about that student (admin, or that student; always 200, with `"available": false` and a plain-language explanation if Gemini isn't configured/reachable)
- `GET /api/gemini_status` — `{"configured": true|false}` (any logged-in user)
- `GET /api/metrics` — model performance on the held-out test split (any logged-in user)
- `GET /api/cohort_summary` — cohort-wide stats for the Overview page: avg GPA/attendance/study hours, % at-risk, GPA histogram, **per-student** at-risk watchlist (**admin only** — it names individual students)
- `GET /api/cohort_aggregate` — cohort **averages only**, no per-student data at all — powers the "how you compare" panel (**any logged-in user**; safe for a student account precisely because it can't leak another student's record)
- `POST /api/students/{id}/checkin` — `{daily_checkin_mood, sleep_hours}` → logs today's check-in, persists it to the database, and returns the student's updated record and a freshly re-run prediction (admin, or that student)

## Database

Student records and user accounts live in a real database through
`db.py` (SQLAlchemy). Set `DATABASE_URL` to use PostgreSQL; leave it unset
and the app uses a local SQLite file (`alt.db`) so nothing needs installing.
Tables are created and seeded from `student_data.csv` / `users.json` on first
start. Check-ins are real `UPDATE`s and survive restarts. To reset to the
original data, delete `alt.db` (or drop the tables) and restart.

## Deploying (Render + GitHub)

1. Push this folder to a GitHub repo (`.env` and `alt.db` are git-ignored).
2. In Render: **New → Blueprint**, select the repo. `render.yaml` creates the
   web service and a free Postgres database and wires `DATABASE_URL`;
   `AUTH_SECRET_KEY` is generated automatically.
3. Optionally add `GEMINI_API_KEY` in the service's Environment tab.
4. Open the service URL. Login with the demo accounts above.

The free web tier sleeps when idle, so the first request after a pause takes
~30-60s to wake. Open it once before presenting. Free Render Postgres
databases expire after a limited period, so redeploy fresh near the review.

## Honest model performance (held-out 20% test split)

- **GPA regressor** (RandomForestRegressor): R² = 0.74, MAE = 0.44 (on a 0–10 scale)
- **Academic-risk classifier** (RandomForestClassifier): Accuracy = 80%, F1 = 0.52, ROC-AUC = 0.78

These numbers come straight from `models/metrics.json`, produced by `train_models.py` — they are not adjusted for presentation.

## Design notes

- The risk classifier uses a tuned decision threshold (0.45 instead of the default 0.5) to trade a little precision for better recall on the minority "at-risk" class (~20% of students) — this is recorded in `models/risk_threshold.pkl` and explained in a comment in `train_models.py`, not hidden.
- Feature importances (shown in the dashboard) come directly from each trained RandomForest, not hardcoded.
